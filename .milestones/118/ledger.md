Final figure, multi-line-aware, verified 2026-08-25:

| census | result |
|---|---|
| #5209's own acceptance grep (`DijkstraEra not yet supported`) | **6** |
| my first re-derivation, single-line regex | 32 error stubs |
| **corrected, multi-line-aware** | **38 error stubs + 6 `pendingWith` = 44, across 15 files** |

The correction came from the epic owner, who normalized string continuations
before counting. Six error stubs span source lines via Haskell's `\...\` string
continuation and are **invisible to any single-line regex** — for example
`mkTransaction: Dijkstra \ \not yet supported`,

`certificateFrom…Ledger: Dijkstra not yet supported`. I re-derived the corrected
figure independently rather than accepting it: 38 + 6 = 44 across 15 files.

**Record this as an instrument failure of mine, not a tidy revision.** My first
census used a single-line regex, found exactly one multi-line case
(`Delegation.hs:145`), noted it as a footnote — and did not generalize from it.
That is precisely the defect I had just finished warning the epic owner about in
its own brief: *a search returning a number is a claim about the method as much
as about the tree.* I had a positive control that the method missed something
and I treated it as an exception rather than as evidence the method was wrong.
The control at the right level is: **normalize the source before counting**,
which is what `evidence/dijkstra-census.sh` in the epic's runtime root now does.

The message shapes are also more numerous than the five first recorded — the
census surfaces stubs carrying no "not yet supported" text at all, such as
`TODO: DijkstraNativeScript conversion` and
`TODO: adapt DijkstraTxBody to ledger-core 1.19`. Any re-cut criterion must be
built from the census script, never from a hand-listed set of message strings.

accepts on `grep -rn "DijkstraEra not yet supported" lib/` returning zero. The
